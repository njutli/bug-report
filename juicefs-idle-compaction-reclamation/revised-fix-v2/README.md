# V2 候选：有预算、按收益选择的冷 chunk 回收

2026-09-29。基于 JuiceFS v1.4.1：`0b90c7db5a929ae6adc5faad948d108efd2c99f9`。

## 状态与结论

已实现源码补丁，并完成原版失败/新版通过的真实 session 回归、memkv/SQLite/隔离 Redis 验证、race、真实对象内容和重启验证。

**这是新的 opt-in 修复候选，验证的是恢复能力和后台工作选择/预算，不是生产 TiKV/Ceph 性能验收。**

修复契约是：满足稳定性和收益条件的冷 chunk，即使原触发被跳过、没有后续用户 IO，仍可被重新发现并在预算内尝试回收。低收益历史允许保留；不以所有文件恢复到最少 slice 数作为普遍目标。

## 1. 相比原候选的关键变化

| 项目 | 原候选 | V2 |
| --- | --- | --- |
| 发现 | 每轮从子树根遍历，按逻辑长度枚举 chunk | 分页枚举持久元数据中的实际 chunk 候选，保留游标 |
| 稳定性 | 没有停写判定 | 完整原始 slice 列表两次指纹一致，且间隔达到 min-age |
| 准入 | 直接调用 ordinary compactor | 在原准入门内重新读完整历史，检查指纹和本批收益 |
| 收益 | 无最低空间收益判断 | 最低回收字节与回收/重写比例双门槛；重复 ID 和批次外引用不重复算收益 |
| 限额 | 串行、每次至多一个普通批次 | 发现页、待观察队列、每轮尝试数、逻辑重写字节均有限额 |
| 错误 | 下轮全树重发现 | 有界退避重试；失败和 CAS 作废也扣除当轮预算 |
| 热点公平性 | 随全树遍历 | 变化中的候选退出队列；预算不足保持 FIFO，后续页可以继续推进 |

保持现有普通读写触发条件；新增 worker 的策略位于独立的 `reclaim.go`，并复用原对象合并和引用替换事务。

## 2. 运行流程

```text
定时器到期
  -> 处理已达到观察间隔的候选
       -> 检查挂载根范围、硬链接和取消状态
       -> 进入现有 ordinary 并发门
       -> 重读完整原始历史；指纹不同则重新等待后续发现
       -> 规划原有普通合并批次，检查预计收益
       -> 扣除尝试次数和逻辑输出字节预算
       -> 执行原合并与 origin/CAS 替换
  -> 按剩余观察队列容量读取下一页候选
  -> 保存游标，等待下一步
```

候选源是现有持久 chunk 记录。进程重启会重置游标和冷却观察时间，但旧引用仍可重新发现；没有新增卷格式或待办表。

## 3. 参数

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `--reclaim-interval` | `0` | 默认关闭；正值启用，每步结束后再等待这个间隔 |
| `--reclaim-min-age` | `10m` | 两次相同完整历史指纹的最小间隔 |
| `--reclaim-scan-limit` | `128` | 每页记录数与待观察候选数上限，内部最大 4096 |
| `--reclaim-max-chunks` | `1` | 每步最多进入对象合并的次数 |
| `--reclaim-max-bytes` | `64M` | 每步逻辑重写字节预算，包括失败/作废尝试 |
| `--reclaim-min-bytes` | `64K` | 本批最低预计空间收益 |
| `--reclaim-min-gain` | `25` | 最低“预计收益/逻辑重写量”，单位百分比 |

供隔离 canary 讨论的参数组合：

```text
--reclaim-interval 1m
--reclaim-min-age 10m
--reclaim-scan-limit 128
--reclaim-max-chunks 1
--reclaim-max-bytes 64M
--reclaim-min-bytes 64K
--reclaim-min-gain 25
```

以上是保守起点，不是通用生产参数。大量积压可能需要很长时间才能处理完，应按可接受回收窗口和单位净收益确定预算。实际存储流量还要使用专用维护挂载的上传/下载限速（Mbps）及并发限制。

## 4. 已验证的主要结果

- 原版相同真实-session 回归在 memkv/SQLite 都停留在 99 条；V2 在无用户读写/手工 compact 时回收为 1 条。
- 并发门跳过、同 chunk 忙、对象失败、客户端重建，以及 `1024 → 25 → 1` 的多批历史恢复通过。
- 三轮各 256 KiB 小覆盖：原扫描安排 192 MiB 重写；V2 安排 0 B。此对照是逻辑合并计划口径。
- 两个相邻有效 slice、稀疏首尾数据中间大空洞：V2 不安排零/负空间收益合并。
- 64 MiB slice 被覆盖 16 MiB 的高收益部分覆盖仍可合并；收益门并非一律禁止部分覆盖。
- 1 TiB 纯空洞文件：memkv 扫描 4 条持久记录，SQLite/Redis 各命中 1 条实际 chunk 记录；均为 0 次 chunk `doRead`，不再逐个探测 16,384 个逻辑 chunk。
- 5 个稀疏文件、每文件位于下标 `0/42/16383` 的实际 chunk，在每页/队列仅 2 条时没有遗漏，并最终完成回收。
- SQLite `EXPLAIN QUERY PLAN` 确认为复合索引 `SEARCH`，避免 OR 游标谓词从索引起点反复 `SCAN`。
- SQLite + 内存对象后端，真实 `vfs.Compact`/DeleteSlice：192 KiB 历史收敛为 96 KiB，有效内容及 CRC 一致，3 个旧对象删除，实际新增 PUT 为 96 KiB。session 重启场景通过。
- 三个真实对象负控各带一个高收益哨兵，确认 worker 确实运行；负控对象重写为 0，哨兵正常回收。
- 新的 meta/VFS 用例及补充的预算、分页用例均以 `-race -count=3` 通过；CLI 配置与完整开发构建通过。

详细命令、统计与未通过的扩展套件见 [test-report.md](test-report.md)。机器可复核数据由 `verify-results.py` 从日志归档重新计算。

## 5. 重要边界

1. **单个指定维护客户端启用。** 当前没有分布式租约或全卷共享预算；其他客户端普通 compactor 仍可能与它竞争。
2. **收益是估计值。** 跨文件 clone/共享 slice、trash 保留会降低或延迟实际回收；本实现保守跳过硬链接文件。
3. **低收益历史会保留。** 例如 64 MiB + 256 KiB 的覆盖在默认门槛下不回收，以避免为了少量收益反复重写大块数据。
4. **逻辑字节限额不等同真实网络字节率。** 对象块读取、压缩、重试和删除成本仍需实测及挂载侧限速。
5. **子树限制作用于合并目标。** 候选元数据枚举仍是全卷分页；深度超过 64 层的祖先链保守排除，命名空间并发变更属于尽力范围检查。
6. **扫描限额不是严格 RPC 限额。** 原始历史和祖先查询是额外操作；Redis SCAN COUNT 也只是服务端工作提示。
7. **取消不是硬实时抢占。** 已进入对象回调或原有无 context 的内存等待，仍可能延迟退出。
8. 本次没有 V2 的真实 TiKV/Ceph 前台 P99、容量收敛、长稳或多维护客户端验收。
