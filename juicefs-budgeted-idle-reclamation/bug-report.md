# 问题报告：普通 compaction 因繁忙被丢弃后没有补偿

[English](bug-report.en.md) · [代码流程与补丁详解](code-flow.md) · [测试报告](test-report.md)

## 1. 现象和问题范围

原现场为 JuiceFS v1.4.1（`0b90c7db5a929ae6adc5faad948d108efd2c99f9`）、TiKV 元数据、Ceph RADOS 对象。128 个 1 GiB 文件经历两小时 256 KiB randrw 覆盖，fio 和完整 CRC 通过。停写后的 289 个样本覆盖约 24 小时 5 分钟，对象池 stored 只下降约 0.144 GiB，终点仍高于写前基线约 89.795 GiB。

原现场还带有独立的 VFS B-catchup 修复；本次原生补丁和离线原版对照不依赖它。空闲观察时 TrashDays=0、NoBGJob=false、MaxDeletes=10；对象 block 为 256 KiB，JuiceFS chunk 为 64 MiB。

原始分析有 686,671 条历史记录、345,921 个完全被覆盖的源 slice。定向手工合并能够回收样本空间。这说明存在需要替换的历史引用，但长轮没有逐次分支追踪，不能把全部空间差额归因于一个条件分支。

**本补丁只修复其中可确定复现的原生机制：已发出的普通合并请求因繁忙被丢弃，现有合并完成后没有补偿。**它不提供全卷历史扫描或跨进程恢复。

## 2. 根因

固定版本的 [pkg/meta/base.go](https://github.com/juicedata/juicefs/blob/0b90c7db5a929ae6adc5faad948d108efd2c99f9/pkg/meta/base.go)：

- `Read` 达到 slice 条数条件时，异步调用普通 `compactChunk`。
- `Write` 在 `numSlices%100 == 99 || numSlices > 350` 时触发；到达硬上限时另有同步 `once` 保护。
- 普通请求遇到 `len(compacting) > 10` 或同 key 已忙，直接返回。
- 现有请求结束时只删除 `compacting` 条目，没有保存和唤醒被跳过的请求。

因此，其他合并即使稍后完成，停写后没有新的读写触发时，被丢弃的请求仍不会继续。仍留在 chunk 历史里的引用也不会因为提高删除并发而自动消失。

## 3. 最小修复内容

仅修改 `pkg/meta/base.go`（+42/-5）：

1. 增加懒分配的 `compactTodo`，沿用现有 compaction key，同 key 的多个忙时请求合并为一个待办。
2. 原普通请求能直接准入时，清除该 key 更早的待办；它会读取当前元数据，覆盖这些较早的请求。
3. 将已准入的原批次主体移入内部函数 `compactChunkAdmitted`，对象合并、批次选择和 origin/prefix/CAS 替换使用原代码。
4. 完成、无可合并内容或错误退出时，释放当前槽位，并在同一把锁内给一个可执行待办预留槽位，然后启动它。这样不会出现“唤醒后又被别人抢走槽位”的漏补偿，也不会一次启动整个待办集合。
5. `once` 的门槛检查可能什么也不做，不能因此消耗一个真正的普通待办。
6. 强制合并递归前只释放一次；外层 defer 再执行时不删除已经转交给重试的槽位。
7. session 取消时清空待办，已准入主体开始前再次检查取消状态。

普通并发门仍是原来的 `>10` 条件，即普通槽位最多 11 个；`once/force` 保留原来的显式调用规则。没有增加定时任务或新的触发入口，已经准入但失败的对象操作也没有被改成自动重试循环。

## 4. 确定性复现与修复验证

测试实际启动合并，在对象回调处用 channel 阻塞：

- **全局繁忙：**占满 11 个真实在途槽位，提交两个其他 chunk 的普通请求，再只释放一个槽位。原版不会处理这些请求；修复后依次转交槽位，仍保持普通并发限制。释放者成功或失败均覆盖。
- **同 chunk 繁忙：**第一次读取历史后追加 99 条映射，再发出 256 次重复请求。原版首次合并后留下 100 条；修复后只有一次合并后的补偿，最终为一条。
- **去重负控：**没有新写入时重复请求，补偿重读发现无需再合并，只有第一次对象重写。
- **生命周期和所有权：**覆盖取消、原对象失败策略、同步门槛检查和强制递归的槽位转交。
- **实际对象：**SQLite + 内存 ObjectStorage，真正执行 `vfs.Compact`。在第一次快照之后追加部分覆盖，补偿后完整内容与 CRC 一致，并核对原对象存在到删除的变化。

测试用测试文件内的辅助入口直接调用原普通 compactor，确保请求确实发生在繁忙窗口；观察原始历史不会触发新的用户 Read。没有人工填充假的活跃槽位。

同一套测试可直接在原版编译：13 个目标叶子用例以 `COMPACT_RETRY_MISSING` 失败，九个负控通过；修复后 22 个叶子用例各通过三次 race。具体证据与命令见测试报告。

## 5. 保证边界

- 对当前客户端内有限的待办，在活跃操作能够结束且客户端继续运行时，提供一次普通批次的补偿机会。
- 同 key 请求会合并；普通单批上限和 `skipSome` 等策略保留，不承诺所有 chunk 最终只剩一个 slice。
- 待办是内存状态，session 退出时丢弃。它不发现重启前的旧积压或从未触发过合并的低条数历史。
- 内存开销随不同待办 key 数增长；按 key 去重并不等于存在硬队列容量上限。持续过载仍可能积压。
- 在途对象操作的取消边界沿用原有行为。补偿以前丢弃的请求会增加实际完成的工作量；保留并发门不等于前台性能已经验收。

这是原生忙时请求补偿，不依赖先前的 V2 扫描方案或其 TiKV 预读修正。两份补丁保持不变；以下更新现场验证，而非把候选升级为生产验收通过。

## 6. 现场验证更新（2026-10-04）

- **上游独立复现**：C8-U0完全不带B-catchup或新旧回收补丁，16 GiB数据集覆盖写后空闲约11.28小时，完整slice引用仍为26.4565 GiB，其中2.4902 GiB被完全覆盖，上传已排空。因此残留现象不是B-catchup存在才会发生。该轮覆盖写中止、最终CRC未做，不能当作完整等量A/B或证明所有残留均由忙时分支引起。
- **纯上游＋本候选**：C9-U1完成16 GiB布局及初始CRC；覆盖写总IO仅57.78/64 GiB便被旧PG延迟保护中止。停写约64分钟后、最终CRC前，引用已回到16 GiB且完全被覆盖引用为0，随后补充全量CRC通过。这是回收与正确性证据，不追认完整轮次通过。
- **实际交付组合短轮**：C11/C12使用B-catchup＋本候选，128 GiB数据集分别完成两小时randrw和randwrite，累计写约159 GiB、232.532 GiB。停写后无用户文件读取或人工回收，分别约2小时34分、3小时05分首次回到128 GiB最小引用，重复确认后才做全量CRC，均通过并正常卸载。
- **仍未闭合的场景**：C13顺序写16 jobs×4 GiB、bs=16M，正式写约1小时45分、累计259.703 GiB后触及容量安全线停止。13:30空间已开始自动释放，但完整回收及最终CRC未完成。不能归因为延迟停测，也不能仅凭容量保护认定候选缺陷。

当前结论是：**可复现的忙时漏处理机制已由候选补偿，真实集群两个两小时场景支持自动回收改善及内容正确性；长期容量上界、所有写形态和前台性能非劣性仍未验收。**回收时间是本环境观察值，不是生产SLA。版本、工作量、证据和保留限制见[测试报告现场章节](test-report.md#field-validation)。
