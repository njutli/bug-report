# 问题报告：低记录数覆盖历史在停写后缺少自动合并触发

2026-10-07。[English](bug-report.en.md)

## 1. 现象及与V2的区别

应用原生忙时补偿V2后，随机场景曾通过回收，但C13顺序覆盖写出现剩余历史未自动消失。C13：16个4 GiB文件，共64 GiB，16M、psync/QD1顺序覆盖写；不使用本地缓存、writeback或async_dio。累计写259.70 GiB，约1小时45分钟触及容量安全线，未完成两小时；原中断不追认为通过。

停写后自动合并发生过，随后停滞。只读元数据快照显示：

| 指标 | C13结果 |
|---|---:|
| 逻辑数据 | 64 GiB，完整覆盖 |
| 完整slice引用容量 | 211.39 GiB |
| 在该子树被完全覆盖的slice容量 | 147.36 GiB |
| chunk数 | 1,024 |
| 记录数分布 | 502个仅1条；522个有6～34条 |
| 上传队列 | 已排空 |

元数据仍持有旧slice引用，所以此阶段不能归因于Ceph删除慢；也不能直接删除这些slice——子树“完全被覆盖”不证明没有共享引用。

V2修复“已经请求合并，但忙时请求丢失”。本问题是“低记录数没有触发请求”或“合并后新写留下低记录数尾部”；**并非V2新引入的机制**。同一诊断在原版与V2均可复现。现场未逐chunk记录来源，不能声称已准确区分全部522个chunk属于哪一种路径。

## 2. 固定版本的根因

底本v1.4.1 / `0b90c7db5a929ae6adc5faad948d108efd2c99f9`。核对本地固定源码的`pkg/meta/base.go`、`pkg/meta/tkv.go`：

1. 写侧按每chunk映射**记录数**，在`numSlices % 100 == 99 || numSlices > 350`触发普通合并，不按被覆盖字节数。
2. 同一范围写5/34/98次后停写，可以留下相应记录而不触发；大slice下无效字节量可能很大。
3. 普通合并读取历史快照后，如果新增少量覆盖写，旧快照替换成功仍可能留尾部；没有新触发则停在此处。
4. 元数据Read达到条件可以另行触发合并，所以“读取/CRC后容量下降”不能证明停写自动回收成功。
5. `cleanupSlices`处理引用计数满足删除条件的slice，不扫描全部文件重建最新映射；TiKV MVCC GC和Ceph内部回收都不能替代缺失的文件slice合并。

## 3. 最小复现

隔离meta测试通过真实Write接口产生低记录数历史，观察原始映射而不调用用户Read：

- 两次/34次重叠写后停止，不直接调用compact；期待自动降至一条。
- 写至99条触发普通合并，阻塞对象回调，在快照后追加少量覆盖，释放后停写；期待尾部自动回收。

在V2测试底本的memkv/SQLite/Redis，9个自动触发目标用例全部以`IDLE_TRIGGER_MISSING`失败；V3同样9项×3次race全部通过。原版/V2共同缺口另有原版overlay诊断，每版8项×3次通过，表示**复现预期残留**，不是修复通过。测试/日志与条件见[test-report.md](test-report.md)。

## 4. V3修改

成功写入后，当chunk有多条记录时，按(inode,index)跟踪；同一chunk去重，写入代次递增，跟踪65,536项封顶。客户端元数据Read/Write安静后，单worker逐项检查：

- 原普通合并/待办未结束时让出，读取前预留同chunk槽位。
- 用latest-wins重建比较raw和live字节，只处理有重叠历史的chunk；不因多条有效、非重叠记录而重写。
- 检查中前台恢复则让出；确需处理时复用普通批次、引擎CAS、引用计数与删除，不强制合并全卷。
- 结束前重读确认；仍有历史、失败或写入代次变化则保留并退避，避免丢尾部/立即忙循环。
- 槽位释放复用V2原子交接；session关闭停止新任务并清除本进程跟踪。

CLI/Config增加`idle-compact-delay`，默认0；只读/no-bgjob禁用。详细流程见[code-flow.md](code-flow.md)。

## 5. 明确不保证的范围

进程内跟踪不持久化、不全卷扫描，不发现挂载前历史或其他客户端独立写入；溢出后覆盖不完整。65,536上限只限制新增队列，V2普通重试map仍无硬上限。静默门是本客户端meta Read/Write，不是集群/对象层全局空闲。多客户端各一个worker；单worker不是带宽限速器，前台恢复也不强制取消在途的一批。

持续写入可使旧对象产生快于合并/删除，不承诺空间永不增长；后端故障、共享引用、回收站保留仍受原机制约束。没有24/72小时写入通过、严格性能A/B、跨重启验收；不能声称“修复所有空间问题、没有任何新增风险”。
