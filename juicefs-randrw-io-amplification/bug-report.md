# JuiceFS v1.4.1随机读写放大：现象与问题

[English](bug-report.en.md)

## 1. 我们遇到了什么

在固定文件集上进行256 KiB、50%读／50%写的随机覆盖测试时，应用读写各约8 MiB/s，而JuiceFS对象层的GET／PUT各约189 MiB/s。我们希望确认，这是否与使用方式或配置有关，还是当前slice合并策略在这类负载下的预期表现。

测试使用JuiceFS v1.4.1，commit为 `0b90c7db5a929ae6adc5faad948d108efd2c99f9`。客户端node1通过Linux FUSE提供文件接口；node2～node4运行TiKV元数据引擎和Ceph对象存储，Ceph共6个OSD，数据池采用EC 4+2。

```text
fio → Linux VFS/FUSE → JuiceFS客户端
                       ├─ TiKV：文件属性及chunk/slice映射
                       └─ Ceph RADOS：保存文件内容的对象
```

卷的BlockSize为256 KiB，客户端 `--max-fuse-io 256K`；关闭本地数据缓存和writeback，未开启 `async_dio`。最大上传／下载并发为150／200，缓冲区300 MiB，保留默认2 MiB预读，关闭自动元数据备份，正常合并及删除机制开启。完整参数和方法见[复现方法](reproduce/README.md)。

## 2. 两类实测结果

### 随机读写：对象IO约为应用IO的23.7倍

独立创建128个256 MiB文件，共32 GiB；开始时每个64 MiB chunk只有一条完整映射。正式运行30分钟，128个job各自执行256 KiB随机读写，每job读、写分别限速64 KiB/s，合计每方向约8 MiB/s。

| 统计项 | 30分钟测试结果 |
|---|---:|
| 应用读取／写入 | 各14.0625 GiB |
| 对象GET／PUT | 333.00317／332.8125 GiB |
| 对象读／写放大 | **23.68023／23.66667倍** |
| 合并登记次数与规模 | 5100次，共318.75 GiB，平均64 MiB／次 |
| fio／对象请求错误 | 0 |

对象PUT恰好等于 `14.0625 GiB前台写入 + 318.75 GiB合并规模`，约95.77%的对象写入可由合并规模解释。

### 单文件：两次小覆盖后的读取触发整段合并

在两个独立64 MiB文件上进行对照。初始化后，每个文件只有一条64 MiB slice映射；本次实际初始化自然得到这一状态，没有为这两个文件执行人工compact。

| 操作 | 单处覆盖 | 两处覆盖 |
|---|---:|---:|
| 覆盖位置 | 16 MiB偏移 | 16 MiB和48 MiB偏移 |
| 应用覆盖写总量 | 256 KiB | 512 KiB |
| 覆盖后原始映射数／有效片段数 | 2／3 | 3／5 |
| 随后应用读取 | 256 KiB | 256 KiB |
| 该次读取及其后台工作产生的GET | 256 KiB | **64.5 MiB** |
| 该次读取及其后台工作产生的PUT | 0 | **64 MiB** |
| 合并次数 | 0 | **1** |

读取前更换为同版本的新挂载进程，确保chunk映射不命中旧客户端缓存；覆盖写、触发读取和最终完整CRC分别统计。两组CRC均通过。正样例的64.5 MiB GET中，64 MiB对应合并范围，256 KiB为前台读取量，另有256 KiB尚未细分来源。

这个小样例的覆盖阶段共写512 KiB，随后再上传64 MiB，合计写放大为129倍；它用于说明触发机制，不代替128文件随机负载测得的约23.7倍。完整数据见[测试报告](test-report.md)。

## 3. 我们对原因的理解

一个chunk可由多个slice映射组合成当前文件内容。小范围覆盖会保留旧slice中未被覆盖的部分，再加上新slice。上游代码中，写入会使该chunk的映射缓存失效；后续读取未命中缓存时，会构建有效片段。当原始记录数或有效片段数达到5时，读路径可以异步请求合并。[Read／Write实现](https://github.com/juicedata/juicefs/blob/0b90c7db5a929ae6adc5faad948d108efd2c99f9/pkg/meta/base.go#L2081)

最小样例的有效内容依次为“旧数据前段、新数据B、旧数据中段、新数据C、旧数据尾段”，正好5段。合并范围仍覆盖64 MiB；对象BlockSize为256 KiB，并不意味着合并只处理256 KiB。合并需要读取当前有效内容，生成新slice并重新上传对应对象，之后再替换元数据映射。[合并范围计算](https://github.com/juicedata/juicefs/blob/0b90c7db5a929ae6adc5faad948d108efd2c99f9/pkg/meta/slice.go#L157)、[实际数据合并](https://github.com/juicedata/juicefs/blob/0b90c7db5a929ae6adc5faad948d108efd2c99f9/pkg/vfs/compact.go#L54)

因此，我们理解主体开销来自反复读取和重写大范围有效数据。并非每个256 KiB写请求都立刻重写64 MiB，具体频率还受读取时机、缓存命中和合并并发控制影响。fio的限速约束应用请求，不限制这些内部合并对象IO。

## 4. 希望社区帮助确认

1. **原因理解是否准确？** 少量覆盖形成5个有效片段后，读取触发整个64 MiB范围的合并，是否属于当前设计在读取性能与合并开销之间的预期取舍？我们的触发链路和字节解释是否准确？
2. **使用方式能否改善？** 对于小块随机覆盖并穿插读取的负载，我们的配置或数据组织是否不合适？有没有推荐的参数、缓存策略或使用方式，可以在不修改源码的情况下降低对象IO放大？
